## Why

报名业务实际发生在班次维度，但当前部分容量判断仍依赖岗位级 `jobs.accepted_count` 或岗位级录用人数统计，容易在班次名额已满、自动审核或并发报名时产生超招或误判。

## What Changes

- 将报名容量限制统一改为班次维度：以 `job_schedules.slots_available` 作为实际可报名容量。
- C 端提交报名时按每个所选 `scheduleId` 校验已通过人数是否小于班次容量，不再依赖 `jobs.accepted_count`。
- 企业端审核报名通过时按该报名对应的 `scheduleId` 校验班次容量，不再用岗位级已通过人数限制。
- 岗位详情、报名确认等 C 端展示继续使用班次剩余名额，确保前后端口径一致。
- 企业 PC 和企业小程序创建/编辑岗位时不需要提交班次容量字段，后端统一使用岗位 `headcount` 写入每个班次的 `slots_available`。
- 岗位新增联系人姓名，企业 PC 和企业小程序岗位表单支持填写联系人姓名与电话。
- 新建/修改班次时从岗位联系人信息同步联系人快照；生成工人已排班时继续冗余联系人快照，供 C 端展示和拨打电话。
- 企业端新增班次管理模块，以班次为核心展示班次名称、日期、时间、地点、联系人、报名统计、招聘人数、剩余名额和考勤概览。
- 企业端支持点击报名人数查看报名人列表，以及每个报名人的审核状态、排班状态、考勤情况、补卡和结算状态。
- 企业端支持修改班次信息，修改只影响后续报名和后续生成的排班；已通过报名和已排班记录保持原快照。
- 企业端支持复制班次、批量创建班次、满员停止报名、班次看板和报名/考勤导出。
- `jobs.accepted_count` 不再作为业务判断来源；数据库字段可暂时保留兼容历史数据和旧查询。

### Modified Capabilities

## Impact

- 后端：影响 `c-service` 报名提交逻辑、`enterprise-service` 报名审核通过逻辑、岗位/班次/排班联系人字段同步、班次管理聚合查询、相关 Mapper 统计方法和测试。
- 前端：企业 PC 和企业小程序新增班次管理页面；企业岗位表单新增联系人姓名；C 端岗位详情、报名确认、排班相关页面展示联系人快照。
- 数据库：复用 `job_schedules.slots_available` 和 `schedule_applications.status`；新增岗位、班次、已排班联系人快照字段和班次名称字段；`jobs.accepted_count` 暂不删除，避免破坏兼容。
- 基础设施：无部署配置变化。
