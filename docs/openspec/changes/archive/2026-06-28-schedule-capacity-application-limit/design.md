## Context

当前数据模型中岗位 `jobs.headcount`/`jobs.accepted_count` 与班次 `job_schedules.slots_available` 同时存在。实际报名记录 `schedule_applications` 关联的是 `schedule_id`，兼职在 C 端也是选择具体班次报名，因此容量判断应以班次为准。继续依赖岗位级 `accepted_count` 会带来快照不一致、自动审核超招、不同班次互相影响等问题。

企业端当前运营视图分散在岗位、报名审核、排班和考勤页面，缺少以 `job_schedules` 为核心的班次管理视图。新增班次模块后，企业可以围绕单个班次查看报名、审核、排班、考勤、补卡和结算状态。

数据流：

```text
企业创建岗位/班次
  -> 后端按 jobs.headcount 写入 job_schedules.slots_available
  -> 后端按岗位联系人写入 job_schedules 联系人快照
  -> C端岗位详情返回每个班次 remainingSlots
  -> 工人选择一个或多个 scheduleId 报名
  -> C端报名接口按 scheduleId 校验容量
  -> 企业审核通过按 scheduleId 再次校验容量
  -> ACCEPTED 报名生成排班，并写入 schedule_shifts 联系人快照
```

班次管理查询流：

```text
企业打开班次管理
  -> 查询 job_schedules + jobs 基础信息
  -> 聚合 schedule_applications 报名统计
  -> 聚合 schedule_shifts / attendance_records 考勤统计
  -> 点击报名人数
  -> 查询该 scheduleId 下报名人列表 + 每人排班/考勤/补卡/结算信息
```

## Goals / Non-Goals

**Goals:**

- 将报名容量校验统一为班次维度。
- C 端提交报名和企业端审核通过都必须使用 `job_schedules.slots_available` 与该班次 `ACCEPTED` 数量判断。
- 自动审核路径也必须防止超出班次容量。
- 保留现有前端按班次展示剩余名额的体验。
- 企业前端创建/编辑岗位时不提交 `slotsAvailable`，由后端从岗位 `headcount` 派生班次容量。
- 企业前端支持填写岗位联系人姓名；班次和已排班保存联系人快照，默认沿用岗位联系人信息。
- C 端展示联系人信息时优先使用班次/已排班联系人快照。
- 企业 PC 和企业小程序提供班次管理模块，展示班次列表、报名人列表、考勤概览和班次操作。
- 班次信息修改只影响后续报名和后续生成排班，已通过报名和已排班记录保持原快照。
- 支持复制班次、批量创建班次、满员停止报名、班次看板和导出报名/考勤数据。
- 停止在业务判断中依赖 `jobs.accepted_count`。

**Non-Goals:**

- 本次不删除数据库字段 `jobs.accepted_count`。
- 本次不重构岗位创建表单的人数交互，只保证班次容量字段被正确使用。
- 本次不引入分布式锁；如需强并发防超卖，可在后续通过数据库唯一/条件更新或事务锁增强。
- 本次不支持每个班次单独编辑不同负责人；班次负责人统一从岗位联系人同步。
- 本次不改变历史已排班记录；历史数据缺少快照字段时通过岗位联系人回退展示。

## Decisions

1. **容量来源使用 `job_schedules.slots_available`**
   - 理由：报名记录绑定 `schedule_id`，容量也应绑定同一维度。
   - 替代方案：继续用岗位 `headcount`。缺点是一个岗位多个班次时无法表达每个班次不同容量。

2. **班次容量写入由后端统一派生**
   - 理由：当前产品只维护岗位招聘人数，企业前端无需重复传每个班次容量，避免前后端字段不一致。
   - 替代方案：前端为每个班次提交 `slotsAvailable`。缺点是当前 UI 没有独立班次容量输入，容易提交默认值造成误写。

3. **联系人信息采用快照冗余**
   - 理由：岗位联系人可能后续修改，报名确认、工人排班和打卡需要稳定展示当时班次的联系人信息。
   - 字段：`jobs.contact_name`、`job_schedules.contact_name/contact_phone`、`schedule_shifts.contact_name/contact_phone`。
   - 替代方案：C 端每次从岗位实时读取联系人。缺点是历史排班会受岗位修改影响，且已排班列表需要跨表补数据。

4. **班次管理以 `job_schedules` 为聚合根**
   - 理由：它代表企业发布给工人选择的可报名班次，能自然聚合报名、排班和考勤。
   - 列表字段：班次名称、岗位名称、日期、时间、地点、联系人、报名人数、待审核人数、已通过人数、已拒绝人数、招聘人数、剩余名额、考勤概览、状态。
   - 详情抽屉：点击报名人数打开报名人列表，展示姓名、手机号、实名状态、报名时间、审核状态、排班状态、签到/签退时间、异常状态、补卡状态和结算状态。
   - 替代方案：继续在报名审核/考勤页面分散查看。缺点是企业无法围绕班次做运营。

5. **班次修改采用快照边界**
   - 理由：已经通过审核或已排班的工人需要稳定的工作安排，不能被后续班次修改隐式改变。
   - 规则：修改 `job_schedules` 只影响后续报名和后续生成的 `schedule_shifts`；已存在 `schedule_shifts` 不自动更新。
   - 容量限制：降低容量时不得低于该班次已通过人数。
   - 时间限制：班次已开始或已结束后，只允许修改联系人或备注类信息，不允许修改日期、时间和容量。

6. **已占用容量统计 `schedule_applications.status='ACCEPTED'`**
   - 理由：只有审核通过才占用班次名额，`PENDING` 不占用名额。
   - 替代方案：统计所有报名。缺点是待审核报名会阻止后续有效报名。

7. **C 端与企业端双重校验**
   - 理由：C 端校验改善用户体验，企业端审核校验保证最终一致性，自动审核也必须走容量校验。

8. **`accepted_count` 暂保留但不参与判断**
   - 理由：避免数据库迁移和旧接口兼容风险；后续可独立清理。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 并发自动审核同时通过导致超出容量 | 在服务层使用事务并按班次实时统计；如后续压力增加，再补数据库锁或条件更新 |
| 前端仍显示岗位招聘人数，用户误解为总容量 | 本次保持现状；后续可将文案调整为“班次名额” |
| `accepted_count` 字段继续存在造成误用 | 增加测试覆盖，移除当前报名判断中的读取依赖 |
| 联系人快照与岗位联系人后续不一致 | 这是快照设计预期；修改岗位后新建/修改班次同步新联系人，历史已排班保持原快照 |
| 班次列表聚合查询较重 | 后端提供分页和按日期/状态筛选，报名人列表按需加载 |
| 企业修改班次后误以为影响已通过人员 | 页面展示确认提示：“已通过/已排班人员不受影响” |

## Migration Plan

1. 修改 C 端报名服务：按所选班次逐个校验容量，移除 `accepted_count` 判断。
2. 修改企业端岗位表单提交：移除 `slotsAvailable` 传参，后端继续用 `headcount` 写入班次容量。
3. 新增联系人相关迁移字段，企业前端岗位表单提交 `contactName/contactPhone`。
4. 修改企业端岗位/班次服务：班次写入和更新时同步岗位联系人；生成已排班时写入班次联系人快照。
5. 新增企业端班次管理 API：列表、报名人明细、修改班次、复制班次、批量创建班次、导出。
6. 新增企业 PC 和企业小程序班次管理页面。
7. 修改企业端审核服务：按报名所属班次校验容量。
8. 如 Mapper 缺少按班次统计已通过数量的方法，补充对应接口和 XML。
9. 更新测试覆盖普通报名、自动审核、企业审核满员拒绝、联系人快照同步和班次管理聚合查询。
10. 部署时执行数据库迁移；历史 `accepted_count` 保留但不再影响报名。
