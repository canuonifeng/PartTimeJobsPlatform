# Proposal: annotation-batch-and-filter

## 背景与问题

标注众包能力（annotation-crowdsourcing）已上线，但存在三个运营与体验缺口：

1. **企业端 PC 职位管理混杂**：`JobList.vue`（招聘计划）将零工(WORK)与标注(ANNOTATION)职位放在同一列表，靠"任务类型"下拉筛选。两类职位的管理语义（计价、批次、报名审核、结算）完全不同，混在一起运营效率低。
2. **标注职位没有批次维护入口**：批次在历史设计中复用 `job_schedules` 表（含 total_items/external_batch_id/status），但企业端只能通过"班次管理"（ScheduleManagement，面向零工的日期/时段语义）间接维护，标注职位页面没有任何批次管理入口；且 `job_schedules` 的日期/时段字段 NOT NULL，标注批次被迫填无意义的时间。
3. **C端找活页快捷筛选不合理**：当前为"任务类型Tab + 全量分类平铺"，缺少运营想要的核心快捷入口（全部/零工/标注/附近/急招）；"急招"前端字段已预留但后端无 `urgent` 字段。

## 变更目标

1. 企业端 PC 将零工职位与标注职位拆分为**两个独立管理模块**（独立菜单、独立列表、独立表单语义）；**零工招聘模块只展示零工类型数据**。
2. 标注职位下提供**批次管理**：新建、编辑、上下线、查看完成进度；批次不再需要日期/时段，每个批次包含**批次代号**与**数据量**信息。
3. C端找活页提供**固定快捷筛选入口**：全部 / 零工 / 标注 / 附近 / 急招。

## 范围

- 包含：
  - 企业端 PC：拆分"零工招聘"（仅 WORK）与"标注任务"（仅 ANNOTATION）两个模块；标注任务模块含职位列表/新建/编辑 + 职位下批次管理（列表/新建/编辑/上下线/进度）
  - 后端：`job_schedules` 日期/时段字段改为可空并新增 `batch_code` 批次代号；`jobs` 新增 `urgent` 字段；标注批次 CRUD/上下线/进度接口；C端搜索支持急招筛选与按距离排序
  - C端：jobList 快捷筛选改造为固定入口；标注详情批次展示（真实数据）
- 不包含（非目标）：
  - 不重构标注任务单/抢单/结算既有链路（继续以 job_schedules 作为批次载体）
  - 不做真实 OSS、不做批次导入导出
  - 不新增批次粒度题目/数据管理（批次仅是代号+数据量+外部ID+进度）

## 验收标准

- [ ] 企业端 PC 菜单出现独立的"标注任务"模块，与"零工招聘"互不混杂；**零工招聘模块只展示零工(WORK)数据**，标注模块列表只显示 ANNOTATION 职位
- [ ] 标注职位详情/列表可进入"批次管理"，可新建批次（**批次代号、数据量必填**，外部批次ID可选，无需日期时段）、编辑、上线/下线、查看已完成/已抢进度
- [ ] 新建的标注批次不要求日期/时段；批次状态独立流转（ACTIVE/CANCELLED）
- [ ] C端找活页顶部固定入口为：全部 / 零工 / 标注 / 附近 / 急招，切换后列表正确过滤
- [ ] "急招"入口只显示企业标记为急招的职位（新增 urgent 字段）
- [ ] "附近"入口按距离升序返回职位
- [ ] platform-service 无关；enterprise-service / c-service 测试通过；双端前端构建通过

## 风险与开放问题

- 风险：`job_schedules` 同时被零工排班使用，日期/时段改可空后需保证零工排班逻辑不受影响（现有代码对 null 已兼容，抢单时判空跳过时间过滤）
- 待确认：
  - "急招"的定义：默认采用**企业发布职位时勾选"急招"标记**（新增 `jobs.urgent` 字段），由企业运营主动标记
  - "附近"的范围：默认采用**有定位时按距离升序排列**（不限定半径）
