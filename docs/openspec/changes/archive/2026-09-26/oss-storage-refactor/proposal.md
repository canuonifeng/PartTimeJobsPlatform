# Proposal: oss-storage-refactor

## 背景与问题

当前系统所有文件上传均为**本地磁盘存储**，三个后端服务（c-service / enterprise-service / platform-service）各自实现一套上传逻辑：

- 上传接口：`/api/worker/files/upload`、`/api/enterprise/files/upload`、`/api/admin/files/upload`
- 存储位置：各自 `uploads/` 本地目录，通过 `/uploads/**` 静态资源映射直接对外提供
- 限制：无 bucket 概念、无访问控制，任何拿到 URL 的人都能直接访问文件

**敏感资料裸露风险**：
- 工人实名认证资料（身份证正反面）URL 明文存库，任何人可访问
- 企业资质文件（营业执照）URL 明文存库，任何人可访问

## 变更目标

引入阿里云 OSS，将文件上传与访问划分为**私有/公有**两类 bucket：

- **私有 bucket**：实名认证资料（身份证/人脸）、企业资质文件（营业执照等）——仅授权人（本人、企业审核人员、平台审核人员）可查看
- **公有 bucket**：职位图片、企业 Logo、培训课件（工人端公开观看）、运营素材、头像——公开可访问

上传链路采用**前端直传（STS 临时凭证）**，私有文件查看采用**后端签发签名 URL**（方案 A）。

## 范围

- 包含：
  - 阿里云 OSS 双 bucket 基础设施与配置（私有 + 公有）
  - 三后端服务新增 STS 凭证签发接口、签名 URL 签发接口、文件访问权限校验
  - 前端（worker-uniapp / enterprise-uniapp / enterprise-pc / platform-pc）上传改造为 OSS 直传
  - 私有文件访问权限矩阵落地（本人 / 企业审核人员 / 平台审核人员）
  - 培训课件、职位图片、企业 Logo、运营素材、头像迁移到公有 bucket
  - 实名认证资料、企业资质迁移到私有 bucket
- 不包含（非目标）：
  - 历史本地已存文件的批量迁移脚本（另行规划，本次只保证新上传文件进入 OSS；提供迁移预留方案）
  - 视频转码/图片处理等 OSS 增值服务
  - CDN 加速接入（后续可加，不影响本设计）

## 验收标准

- [ ] 三个后端服务上传接口改为返回 OSS 对象 key，不再落本地磁盘（或本地仅作 dev fallback）
- [ ] 新增 STS 接口，前端可凭临时凭证直传 OSS（私有/公有分别验通）
- [ ] 私有 bucket 文件无签名 URL 无法访问；签名 URL 过期后失效
- [ ] 实名认证资料仅本人、对应企业审核人员、平台审核人员可获取签名 URL，其余人 403
- [ ] 企业资质文件仅企业本人、平台审核人员可获取签名 URL，其余人 403
- [ ] 前端四处上传场景（实名认证、企业资质/Logo、职位图片、培训课件、头像）均改用直传且构建通过
- [ ] 平台端实名/资质审核页面能正常查看私有文件（签名 URL 可用）

## 风险与开放问题

- 风险：STS 权限策略需精确到前缀，防止越权覆盖他人文件
- 风险：私有 URL 若被前端缓存/外泄，签名过期即失效，需确保客户端不硬编码
- 待确认：历史文件的迁移时机（本次不做，但需评估存量影响）
