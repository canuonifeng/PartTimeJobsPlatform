## 上下文

本项目为兼职 SaaS 管理平台，包含三套子系统：企业端（PC + 小程序）、C 端（微信小程序）、平台管理端（PC）。后端采用 Spring Boot，前端企业端/平台管理端使用 Vue 3 + Element Plus，小程序使用 UniApp。

能力规格已定义在 `openspec/specs/` 下 8 个能力域。

## 目标 / 非目标

**目标：**
- 完成三套子系统的整体架构设计
- 确定服务拆分、数据库共享策略、模块边界
- 定义第一个实施阶段的范围和任务

**非目标：**
- 不涉及具体的前端组件设计和样式方案
- 不涉及 CI/CD 和基础设施部署方案
- 不涉及第三方支付对接的详细接口设计

## 设计决策

### 决策 1：服务拆分 - 3 套独立后端服务

企业端和 C 端共享同一数据库，但独立部署为两套 Spring Boot 服务。平台管理端独立部署，通过 API 调用业务系统数据。

理由：
- 企业端和 C 端数据高度耦合（岗位、排班、报名、打卡在同一库），共享库避免数据不一致
- 服务分离允许独立扩缩容和发布，企业端高并发场景（发薪批次）不影响 C 端用户
- 平台管理端为内部运营工具，独立部署保证安全性，不与外部 API 混在一起

### 决策 2：模块化单体架构

每个服务内部按领域模块组织（岗位、排班、结算、人员、企业、用户），模块间通过 interface 调用，不跨模块直接访问数据库。

理由：
- 保持代码组织清晰，后续拆微服务时模块边界已就绪
- MVP 阶段单服务部署简单，不增加运维复杂度

### 决策 3：数据库共享

企业端服务和 C 端服务读写同一 MySQL 实例和同一套表。

理由：
- 岗位、排班、报名、打卡等核心实体天然跨两端使用
- 避免跨服务数据同步的延迟和一致性问题

### 决策 4：薪资混合模式设计

一个岗位支持多条 JobRate 记录（时薪/日薪/计件）。Payroll 模块根据考勤数据和岗位定义的时间段自动匹配适用的薪资规则。

理由：
- 混合业务场景（零售+活动+配送）需要灵活薪资配置
- 规则数据化比硬编码更易扩展

## 关键数据流

### 岗位发布
企业端写 job + job_rate + job_schedule 表 → C 端直接读 → 兼职报名写 job_application → 企业端读 + 更新状态

### 打卡考勤
C 端写 attendance_record → 企业端读并汇总考勤报表 → 结算模块读取计算薪资

### 薪资结算
企业端发起 payroll_batch → 系统计算 → 企业财务确认 → C 端可见收入 → 兼职提现

## 风险 / 权衡

| 风险 | 应对 |
|------|------|
| 两套服务共享数据库，表结构变更需协调 | 使用 Flyway 管理迁移，两端共用迁移脚本 |
| 模块化单体后续拆微服务需重构 | 模块间通过 interface 调用，改微服务时只需替换 interface 实现 |
| 平台管理端调用业务数据依赖 API | 定义内部 API 契约，采用 Feign 声明式调用 |
