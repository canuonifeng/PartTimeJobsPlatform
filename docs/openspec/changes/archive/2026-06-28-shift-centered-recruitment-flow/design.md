## Context

企业端当前已有职位管理、报名审核、班次管理、考勤确认和薪资结算能力，但产品表达仍以“职位/岗位”为主入口。近期已经完成班次容量、班次联系人快照和班次管理页面，说明业务事实已经从岗位级转向班次级：工人选择具体班次报名，企业按班次审核容量，排班、打卡、补卡、薪资结算都落到具体班次或工人排班记录。

这次设计不是推翻现有数据模型，而是统一产品心智和入口关系：`jobs` 继续作为招聘计划/岗位模板，`job_schedules` 作为招聘和运营单元，`schedule_applications`、`schedule_shifts`、`attendance_records`、结算记录围绕班次串联。

架构关系：

```text
企业招聘
├── 招聘计划 jobs
│   ├── 岗位名称/要求/薪资/地点/联系人
│   └── 生成或维护多个班次 job_schedules
├── 班次 job_schedules
│   ├── 报名 schedule_applications
│   ├── 录用后排班 schedule_shifts
│   ├── 打卡考勤 attendance_records
│   └── 薪资结算 settlement/balance records
└── 展示终端
    ├── enterprise-pc: 完整管理与批量处理
    ├── enterprise-uniapp: 今日待办和轻操作
    ├── worker-uniapp: 按班次报名、上岗、打卡
    └── site-index/docs: 对外产品表达
```

核心数据流：

```text
企业创建招聘计划
  -> 设置班次日期/时间/人数
  -> 发布班次招聘
  -> 工人端按 scheduleId 报名
  -> 企业按班次审核报名
  -> 审核通过生成 schedule_shift
  -> 工人签到/签退生成 attendance_record
  -> 企业确认考勤/处理补卡
  -> 按班次或工人结算薪资
```

服务边界：

- `enterprise-service`：招聘计划、班次工作台、报名审核、考勤确认、结算上下文的主服务。
- `c-service`：工人端职位浏览、班次报名、我的排班、打卡、收入展示，读取同一业务数据但保持 C 端 API 前缀与 VO 独立。
- `platform-service`：不参与日常招聘流程，只在平台运营配置、审核或产品文案需要时同步。
- `site-index`：独立官网项目，只更新静态产品文案、视觉和静态测试，不耦合业务 API。

## Goals / Non-Goals

**Goals:**

- 统一企业端招聘产品心智：岗位/职位是招聘计划，班次是实际招聘和运营单元。
- 企业 PC 支持从招聘首页进入班次上下文，围绕待审核、待确认、异常考勤、待结算完成闭环。
- 企业小程序支持移动端轻操作：今日班次、班次详情、报名人、更多操作、待办统计。
- 工人端在岗位详情、报名确认、报名成功、我的排班和打卡页统一使用“班次”语义。
- 后端聚合接口支持班次工作台所需的统计、状态、报名人、考勤、补卡和结算信息。
- 产品文档和官网统一新流程描述，避免“职位发布 → 排班”与实际“班次报名”冲突。
- 保持现有数据库和接口兼容，尽量通过新增聚合接口、VO 字段和前端文案完成升级。

**Non-Goals:**

- 不删除 `jobs` 表或历史字段。
- 不一次性重命名所有代码中的 `Job` 类或 `jobs` API，避免大规模破坏性变更。
- 不重做支付、提现、平台审核、账户权限等非招聘主流程能力。
- 不引入新的前端 UI 框架、后端中间件或外部依赖。
- 不把官网 `site-index` 合并进主业务仓库；它仍作为独立静态站点维护。

## Decisions

### Decision 1: 保留 `jobs` 数据模型，但产品名升级为“招聘计划”

- 选择：数据库和后端核心实体继续使用 `Job`/`jobs`，前端导航和产品文案逐步改为“招聘计划”或“岗位模板”。
- 原因：历史数据、接口、C 端页面和测试大量依赖 `Job`，物理改名成本高且风险大。
- 替代方案：全量重命名 `jobs` 为 `recruitment_plans`。该方案语义更干净，但会影响迁移、接口兼容、MyBatis XML、前端 API、测试和线上数据，不适合当前阶段。

### Decision 2: 班次作为招聘运营主入口

- 选择：企业端日常运营页面以 `job_schedules.id` 为主上下文，报名、录用、考勤、补卡、结算都可从班次详情进入。
- 原因：容量限制、报名记录、考勤记录都天然关联班次，企业负责人关心的是“某天某时间这班有没有招满、谁来、谁异常、谁要结算”。
- 替代方案：继续以岗位为入口，在岗位详情里展示所有报名和排班。该方案适合低频管理，但多班次场景下信息过密，移动端尤其难用。

### Decision 3: 分阶段调整前端导航，不一次性删除旧页面

- 选择：新增或强化招聘首页/班次工作台，同时保留职位管理、报名审核、考勤确认、薪资结算独立页面，并通过班次上下文互相跳转。
- 原因：企业用户可能已经习惯旧入口，直接删除会造成学习成本和权限风险。
- 替代方案：完全用班次详情替代报名审核/考勤确认/薪资结算页面。该方案更聚焦，但会牺牲批量处理效率。

### Decision 4: 后端优先补聚合接口和状态枚举中文映射

- 选择：保留既有 CRUD 接口，新增或扩展班次工作台接口，如班次汇总、班次详情、报名人、考勤概览、结算概览、操作入口状态。
- 原因：前端页面需要一次性展示跨表状态，避免移动端多次请求和字段不一致。
- 替代方案：前端分别调用报名、排班、考勤、结算接口后自行拼接。该方案后端改动少，但移动端性能和一致性较差。

### Decision 5: 文档和官网与产品重构同步交付

- 选择：同一变更内包含 README、系统概述、前后端规范、官网文案、官网视觉和静态检查更新任务。
- 原因：本次是产品心智变化，不只是代码功能；官网是产品对外入口，必须同步表达。
- 替代方案：代码先改，文档和官网以后补。该方案交付快，但会造成销售/演示/用户理解不一致。

## Risks / Trade-offs

| Risk | Mitigation |
|---|---|
| “招聘计划”和“职位/岗位”并存导致用户混淆 | 前端文案统一使用“招聘计划”，必要处用副标题说明“原职位/岗位信息”。 |
| 班次工作台聚合查询变复杂，影响性能 | 分页查询，按 companyId、scheduleDate、status 建议索引，聚合只返回当前页面必要字段。 |
| 旧接口仍使用 `/jobs`，与新文案不一致 | API 层暂不破坏兼容，前端 API 文件可逐步增加 recruitment alias，文档说明兼容关系。 |
| 官网和业务仓库分离，容易漏提交 | 实施任务中单列 `site-index` 仓库检查、构建、提交和推送步骤。 |
| 移动端班次详情承载过多功能 | 小程序只保留轻操作，批量管理和复杂筛选放在企业 PC。 |
| 工人端仍看到“岗位”而企业端使用“招聘计划” | 工人端保留“职位/岗位”面向用户的自然表达，但报名动作明确为选择班次。 |
| 历史数据缺少班次联系人、状态或结算关联 | 复用已有迁移脚本和修复脚本，必要时新增幂等数据修复 SQL。 |

## Migration Plan

1. 规格和文档阶段：先确认新术语、流程、页面信息架构和官网文案。
2. 后端阶段：补班次工作台聚合接口和必要 VO 字段，确保旧接口兼容。
3. 企业 PC 阶段：调整招聘导航、招聘计划页面、班次详情/工作台、跨页面跳转和待办统计。
4. 企业小程序阶段：调整首页入口和班次详情轻操作，保持已开发班次管理页面风格一致。
5. 工人端阶段：统一报名确认、报名成功、我的排班、打卡等班次文案。
6. 文档阶段：更新 README、英文 README、系统概述、前后端规范和产品说明。
7. 官网阶段：在 `site-index` 更新首页文案、视觉模块、SEO 和静态检查。
8. 发布阶段：先部署后端，再部署 PC/H5/小程序，最后发布官网。

Rollback 策略：

- 若后端聚合接口异常，前端保留旧页面入口和旧接口路径，可临时隐藏班次工作台增强模块。
- 若文案引起用户困惑，可保留“招聘计划（职位）”双名称过渡。
- 官网可单独回滚到上一静态版本，不影响业务系统。

## Open Questions

- 企业端导航最终名称用“招聘”还是“用工”？当前建议使用“招聘”。
- PC 端是否将“职位管理”完全改名为“招聘计划”，还是采用“招聘计划（职位）”过渡一个版本？
- 班次详情中是否直接提供“录用/拒绝”操作，还是仍跳转到报名审核页处理？当前建议详情内可处理单个报名，批量保留报名审核页。
- 薪资结算是否允许从班次详情直接结算单人，还是只展示状态并跳转薪资管理？当前建议支持单人结算。
- 官网是否需要新增独立“解决方案”页描述班次中心招聘闭环，还是先改首页已有模块？当前建议先改首页和 solutions 页面。
