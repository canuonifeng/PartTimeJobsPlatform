## Why

当前企业端招聘流程仍以“职位/岗位”为主要入口，但实际业务已经围绕“班次”发生：工人报名具体班次、容量限制按班次计算、企业审核后生成排班，后续考勤与结算也都与班次强相关。继续以职位为中心会让企业在岗位、报名、排班、考勤和结算之间来回切换，运营效率低且产品表达不一致。

本次改造将企业招聘流程升级为“招聘计划 + 班次中心”的产品模型，让企业从创建招聘计划、开放班次报名、处理报名、执行考勤到结算收尾形成统一闭环，并同步调整产品说明文档和官网文案。

## What Changes

- 企业端招聘业务主流程从“发布职位 → 工人报名 → 企业审核 → 排班 → 打卡考勤 → 薪资结算”升级为“创建招聘计划 → 创建班次 → 发布班次招聘 → 报名审核 → 班次执行 → 考勤确认 → 薪资结算”。
- 将“岗位/职位”产品定位调整为“招聘计划/岗位模板”，承载岗位名称、薪资规则、地点、岗位要求、联系人等可复用信息。
- 将“班次”定位为真正的招聘单元，承载日期、时间、招聘人数、报名人数、录用人数、考勤异常和结算状态。
- 企业 PC 端调整招聘相关信息架构：招聘首页、招聘计划、班次管理、报名审核、考勤确认、薪资结算之间形成班次上下文联动。
- 企业小程序强化移动端轻操作：今日班次、待审核报名、异常考勤、待结算薪资、班次详情工作台。
- 工人端展示继续面向岗位详情，但报名确认、报名成功、我的排班等文案统一说明“按班次报名/上岗”。
- 后端接口和 VO 命名逐步体现班次中心语义：列表、统计、报名审核、考勤确认、导出和结算都应支持 `scheduleId` 上下文。
- 产品文档同步更新：`README.md`、英文 README、`docs/系统概述.md`、前后端技术/产品说明、OpenSpec 规格需统一新流程描述。
- 官网 `site-index` 文案和视觉模块同步调整：将产品卖点从“职位发布和排班”升级为“班次中心招聘运营闭环”，并美化首页流程、痛点、能力卡片和 CTA。
- 不删除历史 `jobs` 或旧接口字段；对外接口保持兼容，避免破坏已上线 C 端和企业端流程。

## Capabilities

### New Capabilities
- `shift-centered-recruitment`: 定义招聘计划与班次中心招聘流程、企业端班次工作台、文档和官网表达统一规则。

### Modified Capabilities
- `job-management`: 岗位/职位能力从单一招聘入口调整为招聘计划/岗位模板，报名、容量和运营入口以班次为核心。
- `schedule-attendance`: 班次能力从排班执行扩展为招聘运营核心，包括班次报名统计、报名人详情、执行状态、异常考勤和收尾动作。
- `payroll`: 薪资结算需要支持从班次上下文查看和触发单个工人/单个班次的结算状态。
- `notification`: 招聘计划发布、班次报名、报名审核、班次变更和结算收尾的通知文案需统一为班次中心语义。

## Impact

- 后端：影响 `enterprise-service` 招聘、班次、报名、考勤、结算接口语义和聚合查询；`c-service` 岗位详情、报名、排班和通知展示需保持班次语义；不涉及 `platform-service` 核心流程，仅可能更新平台端产品说明或配置文案。
- 企业 PC：影响招聘导航、职位/招聘计划页面、班次管理、报名审核、考勤确认、薪资结算、首页待办统计和页面文案。
- 企业小程序：影响首页快捷入口、招聘/班次页面、报名人抽屉、班次详情、编辑/复制/批量创建、移动端待办入口。
- 工人端：影响岗位详情、报名确认、报名成功、我的排班、打卡页的字段文案和跳转说明。
- 官网 `site-index`：影响首页 hero、痛点、功能能力、流程说明、CTA、SEO title/description、静态检查用例和样式美化。
- 文档：影响 `README.md`、英文 README、`docs/系统概述.md`、`docs/前端技术规范.md`、`docs/后端技术规范.md` 中与产品流程、URL、模块职责相关描述。
- 数据库：优先复用现有 `jobs`、`job_schedules`、`schedule_applications`、`schedule_shifts`、`attendance_records` 和结算表；仅当班次详情工作台缺失必要字段时新增迁移脚本。
- 基础设施：无新增外部依赖；官网和业务仓库可能需要分别提交/推送。
